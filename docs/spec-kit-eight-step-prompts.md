# 股票分析智能体：Spec Kit 八步话术

本项目已使用 Codex skills 模式初始化 Spec Kit。请在项目根目录中按顺序执行以下
八个技能。每一步完成并检查产物后再进入下一步；不要一次性跳到实现。

## 第一步：建立项目宪法

```text
$speckit-constitution

为“本地量化股票分析智能体”建立项目宪法，采用 1.0.0 作为首个正式版本，批准日期
为 2026-07-10。把以下规则写成可检查、不可绕过的 MUST 原则，并同步检查 Spec Kit
相关模板：

1. 本地数据是量化事实来源。所有行情、板块、特征、预测、实际结果、报告和模型版本
   必须本地持久化，并记录来源、市场时间、采集时间和数据版本。
2. 严禁未来数据泄漏。训练、验证和回测必须按时间顺序切分；任何特征只能使用预测
   时点已经可获得的数据。
3. 大模型只负责意图理解、工具编排和结果解释。它不得凭空生成行情或预测数字，所有
   数字必须能追溯到 MCP 工具结果。
4. 预测必须表达为指定周期内上涨、震荡、下跌的概率，并附置信度、主要依据、数据
   新鲜度、模型版本和风险因素；不得承诺收益。
5. 自学习只能产生候选模型。候选模型必须依次通过时间序列回测、简单基准比较、影子
   运行和人工批准，才能发布；发布必须可回滚。
6. 原始行情和预测快照必须追加保存，禁止静默覆盖。修订必须形成带来源的新版本。
7. 行情更新、回测和训练必须与 PySide6 界面隔离，失败不得破坏桌面应用或已验证数据。
8. 第一阶段只提供研究、模拟预测和历史验证，不连接券商，不执行真实交易。
9. Skill、MCP 和内部服务必须具有结构化契约、最小权限、参数校验、错误处理、日志和
   自动化测试。
10. Windows、macOS 和 Linux 是正式目标平台，平台差异必须集中封装并分别验收。
11. 项目自行编写的文档、代码注释、文档字符串和示例说明必须使用简体中文。代码
    标识符、协议字段、第三方 API 名称和专有技术名词可以保留英文；第三方原文必须
    提供中文解释。注释必须解释业务规则或非显然理由，不得机械重复代码含义。

治理要求：任何规格、计划或任务与宪法冲突时必须停止；修改宪法需要说明原因、版本
变化和受影响产物。所有预测界面和报告必须显示“研究参考，不构成投资建议”。
```

**预期产物**：`.specify/memory/constitution.md`

## 第二步：生成产品规格

```text
$speckit-specify

创建“本地量化股票分析智能体”产品规格，描述用户需要什么和为什么，不在本步骤指定
编程语言、框架、数据库或模型算法。

目标用户是使用个人电脑研究股票的个人投资研究者。用户需要通过一个桌面程序完成：

- 查看 A 股、港股、美股的市场状态、主要指数、实时或准实时行情和历史行情；
- 查看行业、概念、地域等主要板块，创建和维护自定义板块；
- 查看板块涨跌、成交活跃度、上涨下跌家数、趋势强度和板块轮动；
- 查看个股 K 线、成交量、指标、所属板块及相对大盘和板块的强弱；
- 获得未来 1 日、5 日、20 日上涨、震荡、下跌的概率、置信度、依据和风险因素；
- 用自然语言询问行情、板块、个股、预测、回测和历史报告；
- 每日自动更新数据并生成市场总结、强弱板块、关注个股和预测复盘；
- 查看每次历史预测、到期实际结果以及模型相对简单基准的表现；
- 查看候选模型的训练、回测、影子运行和人工批准状态；
- 在 Windows、macOS、Linux 上保存并恢复本地数据、设置和任务状态。

规格必须包含可独立验收的优先级用户故事、异常和边界场景、关键实体、明确的范围外
内容以及技术无关、可量化的成功标准。

关键约束：

- 第一阶段不连接券商、不自动下单；
- 行情必须显示来源、市场时间、采集时间和新鲜度，延迟数据不得标记为实时；
- A 股、港股、美股分别处理证券代码、时区、交易日历、交易时段和币种；
- 自定义板块保存成员变更历史，历史分析只能使用当时有效的成员；
- 大模型不能脱离结构化工具返回值生成量化数字；
- 数据源失效时必须明确降级，不能使用过期数据伪装实时预测；
- 所有项目自编写的规格和说明文档使用简体中文；
- 所有预测只作为研究参考，不构成投资建议。
```

**预期产物**：`specs/<feature>/spec.md` 和
`specs/<feature>/checklists/requirements.md`

## 第三步：消除关键歧义

```text
$speckit-clarify

审查当前规格并把答案直接写回规格。优先识别会改变架构、数据模型、验收标准或合规
边界的歧义。每次只问一个问题，最多五个；已经确认的内容不要重复询问。

重点检查：

- “实时”对三个市场分别允许多大延迟，界面如何展示新鲜度；
- 数据源授权、用户自带凭据和无凭据时的降级范围；
- 上涨、震荡、下跌在 1 日、5 日、20 日周期中的可检验定义；
- 新闻和市场情绪是否属于首个可验收版本；
- 分钟线保留期限、预期股票数量和本地磁盘规模；
- 每日任务在各市场开盘前、盘中和收盘后的执行时点；
- 候选模型相对基准的最低发布门槛及人工批准角色；
- 数据导入导出、备份、恢复和删除的用户预期；
- 桌面端关键页面的空状态、加载状态、离线状态和恢复流程；
- MCP 对外开放范围和涉及发布、回滚、删除时的权限边界。

如果规格已经给出合理且可测试的答案，将对应类别标记为 Clear，不要为了凑数量而
提问。完成后报告修改过的章节和仍适合留到技术计划阶段处理的事项。
```

**预期产物**：更新后的 `spec.md`，包含当日 Clarifications 记录。

## 第四步：制定技术计划

```text
$speckit-plan

基于已经确认的规格和宪法，为跨平台本地桌面应用制定技术计划。

采用以下已确认方向：

- Python 作为主要语言，PySide6 构建 Windows、macOS、Linux 桌面端；
- 模块化本地架构：桌面进程、本地应用服务、后台任务队列、独立训练进程和 MCP Server；
- DuckDB 保存证券、板块、预测、结果、任务和模型元数据；
- Parquet 保存分钟线、日线和特征快照；
- SQLite 保存桌面设置、窗口状态、用户偏好和对话索引；
- 模型注册表保存模型文件、训练参数、代码版本、数据范围、特征版本和评估报告；
- 行情使用可插拔适配器，技术研究阶段比较授权范围、三大市场覆盖、延迟、稳定性、
  限频、成本和跨平台可用性，不把核心服务绑定到单一供应商；
- Skill 编排每日分析、个股诊断、板块轮动、预测复盘和模型评估；
- MCP 提供结构化、可审计、默认只读的行情、指标、预测、回测、报告、任务和模型查询
  工具；发布、回滚和删除需要单独权限与桌面端确认。

计划必须生成 research.md、data-model.md、quickstart.md 和 contracts/。接口契约至少覆盖
市场行情、板块、自定义板块、预测、回测、报告、任务、模型和 MCP 工具。明确进程边界、
任务状态机、数据版本策略、跨市场时区/交易日历/币种处理、平台目录、备份恢复、日志、
错误降级、性能目标和跨平台打包方案。

回测必须使用时间滚动或扩展窗口，包含手续费、滑点、停牌和不可成交约束。正式模型
发布前必须通过简单基准比较和至少 30 个交易日的影子运行。任何未解决的关键技术问题
都要在 research.md 中给出决定、理由和被否决方案，不得把 NEEDS CLARIFICATION 留到
任务阶段。
```

**预期产物**：`plan.md`、`research.md`、`data-model.md`、`quickstart.md`、
`contracts/`。

## 第五步：生成需求质量清单

```text
$speckit-checklist

为正式评审生成一份高严格度的“量化数据、预测安全、桌面体验与 MCP 契约”需求质量
清单。清单用于检查规格和计划是否完整、清晰、一致、可衡量，而不是测试实现代码。

清单重点覆盖：

- 三大市场代码、时区、交易日历、复权、币种和跨市场比较规则是否写清楚；
- 主要板块、自定义板块和历史成员关系是否具有明确需求；
- 行情来源、授权、新鲜度、冲突、限频、缺失和降级规则是否完整；
- 上涨、震荡、下跌标签及 1 日、5 日、20 日预测周期是否可测量；
- 是否明确禁止未来数据泄漏，并定义训练、回测和预测快照边界；
- 概率校准、简单基准、手续费、滑点、停牌和不可成交条件是否有验收标准；
- 候选模型、影子运行、人工批准、发布失败和回滚需求是否完整；
- MCP 输入输出、权限、超时、错误、审计和大模型数字溯源是否明确；
- PySide6 页面、空状态、加载状态、离线状态、后台任务和崩溃恢复是否有需求；
- Windows、macOS、Linux 的安装、升级、存储目录和恢复边界是否清晰；
- 项目文档、代码注释和文档字符串的简体中文要求是否完整、一致且可检查；
- 不自动交易、不承诺收益和投资风险提示是否在所有相关产物中一致。

至少 80% 的条目必须引用规格章节或使用 Gap、Ambiguity、Conflict、Assumption 等
追踪标记。不要写“测试按钮是否可用”一类实现测试项。
```

**预期产物**：`specs/<feature>/checklists/quant-agent.md`

## 第六步：拆分可执行任务

```text
$speckit-tasks

根据规格、计划、数据模型、契约、研究记录和质量清单，生成按用户故事组织、具有依赖
顺序并可独立验收的 tasks.md。项目要求测试驱动开发；每个用户故事的契约测试、数据
测试和失败场景测试必须先于实现任务。

建议按以下增量组织，但必须服从规格中的用户故事优先级：

1. 项目结构、依赖管理、跨平台配置、日志和测试框架；
2. 证券主数据、交易日历、板块成员历史、本地数据库和迁移备份；
3. 一个市场的历史日线采集、标准化、特征、简单基准、时间序列回测和本地展示闭环；
4. A 股、港股、美股适配器和数据新鲜度/冲突/降级处理；
5. 主要板块、自定义板块、板块强弱和轮动分析；
6. 1 日、5 日、20 日概率预测、解释、快照和到期结果回填；
7. MCP Server、工具契约、最小权限和调用审计；
8. AI 对话 Skill 与数字溯源；
9. 每日调度、报告、任务恢复和通知；
10. 候选模型训练、基准比较、影子运行、人工批准、发布和回滚；
11. Windows、macOS、Linux 打包、升级和端到端验收。

所有任务必须使用 Spec Kit 规定格式：复选框、连续任务 ID、必要的并行标记、用户故事
标签、清晰动作和准确文件路径。标明用户故事依赖、可并行任务以及首个 MVP 范围。
```

**预期产物**：`specs/<feature>/tasks.md`

## 第七步：只读一致性分析

```text
$speckit-analyze

对 constitution.md、spec.md、plan.md 和 tasks.md 执行严格的只读一致性分析。不要在本
步骤修改任何文件。

除常规重复、歧义、覆盖缺口和术语漂移外，重点检查：

- 是否有任务绕过宪法规定的数据溯源、未来数据泄漏防护或模型发布门禁；
- 三大市场、主要板块、自定义板块和跨平台桌面端是否被规格、计划和任务完整覆盖；
- 数据实体是否覆盖原始行情、标准化行情、板块成员历史、特征快照、预测快照、实际
  结果、模型版本、任务和审计记录；
- MCP 契约是否映射到明确需求和任务，大模型是否可能绕过工具生成量化数字；
- 回测是否遗漏简单基准、概率校准、手续费、滑点、停牌或不可成交条件；
- 自学习是否可能直接覆盖正式模型，是否缺少影子运行、人工批准或回滚任务；
- Windows、macOS、Linux 的构建与验证是否有对应任务；
- 每项核心需求是否至少映射到一个具体任务，是否存在没有需求依据的任务。

输出严重级别、文件位置、修复建议、需求覆盖率和未映射任务。存在 CRITICAL 或 HIGH
问题时明确阻止进入实现，并等待用户批准后再另行修订。
```

**预期产物**：终端中的只读 Specification Analysis Report。

## 第八步：分阶段实施与验证

```text
$speckit-implement

先检查所有需求质量清单和 tasks.md。任何清单未完成、任何 CRITICAL/HIGH 一致性问题
未解决，或核心契约缺失时停止并报告，不要强行继续。

严格按 tasks.md 的依赖和用户故事阶段实施：

- 每个功能先写失败测试，再写最小实现使测试通过；
- 每完成一个任务立即运行相关测试，并在 tasks.md 中标记完成；
- 后台数据更新、回测和训练不得阻塞 PySide6 界面；
- 任何行情和预测数字必须带来源、时间和版本，并能从 AI 回答追溯到 MCP 工具；
- 不得使用未来数据，不得修改已经产生的预测快照；
- 不得添加券商登录、真实下单或自动交易；
- 数据源凭据不得提交到 Git，日志不得泄露密钥；
- 项目自行编写或修改的代码注释、文档字符串、示例和说明文档必须使用简体中文；
- 分阶段执行数据契约、模型评估、MCP 契约、桌面关键流程和跨平台测试；
- 非并行任务失败时立即停止，保留已完成工作并报告根因和恢复方法。

首个 MVP 必须先完成一个可运行闭环：历史日线采集 → 本地存储 → 特征计算 → 简单
基准预测 → 时间序列回测 → MCP 查询 → AI 解释 → PySide6 展示 → 每日报告。

高级模型、自学习和正式模型发布只能在 MVP 验收后实施。候选模型必须通过时间序列
回测、简单基准比较和至少 30 个交易日的影子运行，并由用户在桌面端明确批准。完成后
输出已完成任务、测试结果、已知限制、数据源状态和跨平台构建状态。
```

**预期产物**：按 `tasks.md` 实现的代码、测试、构建产物和验收报告。

## 执行原则

1. 八步必须按顺序执行。
2. 第三步可以没有问题，但不能跳过歧义扫描。
3. 第五步检查“需求写得是否合格”，不是检查代码。
4. 第七步只读；发现问题后必须单独获得修订授权。
5. 第八步不是一次性完成全部愿景，先交付可运行的最小闭环。
6. 所有真实或准实时行情必须来自用户有权使用的数据源。
7. 预测结果必须可复现、可评估、可回滚，且不构成投资建议。
